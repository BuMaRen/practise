# 系统设计学习手册

这份手册是长期学习材料，不对应某一道题的答案。设计的目标是满足业务结果和验收约束，并让关键取舍可解释、可验证。

## 一、从需求走到可评审设计

### 1. 分清事实、问题和假设

先整理题目已经给出的背景、必须满足的功能和质量指标。把会改变方案的未知项列成澄清问题，例如用户角色、峰值和持续时间、数据保留、失败后的业务处理。无法获得答案时写出假设、选择该假设的理由，以及假设变化会影响什么。避免把假设说成事实。

### 2. 定义成功和边界

把需求拆成用户可观察的结果、系统责任、外部依赖和不在范围内的事项。将“快、可靠、安全”等词转换为可观测的服务指标；分别识别延迟、吞吐、可用性、数据正确性、恢复能力和成本约束。不同质量目标可能冲突，需指出优先级。

### 3. 建立量级模型

根据活跃用户、请求频率、峰值系数、读写比例和业务事件估算平均与峰值吞吐。计算并发、单条数据大小、保留周期带来的存储增长、复制和索引开销、网络流量。注明单位和假设，并用结果检查瓶颈；量级估算用于决定下一步调查，不是伪精确预测。

常用关系：

- 峰值吞吐 ≈ 日请求量 ÷ 86400 × 峰值系数。
- 并发请求 ≈ 吞吐 × 平均处理时间（Little 定律）。
- 原始存储 ≈ 日新增记录数 × 平均记录大小 × 保留天数；再单独考虑索引、副本和增长余量。
- 带宽 ≈ 每秒请求数 × 平均传输字节数。

### 4. 从用例推导接口和数据

列出核心读写操作、调用方、数据责任边界、身份与权限边界。为关键实体定义生命周期、状态变化、唯一性、保留和删除规则。选择存储时从访问模式、事务、一致性、查询、写入规模和运维能力出发；不要先选数据库再强行适配需求。接口应明确分页、错误语义、超时、幂等和版本演进。

### 5. 画出边界并走通主流程

先画参与者、信任边界和依赖，再补数据存放位置及关键通信路径。逐条沿关键用例说明读写发生在哪里、成功如何确认、客户端观察到什么。图表达边界与关系，文字解释时序和责任；图中的每条边都应能解释。

### 6. 按故障路径推演

至少检查客户端重试、重复提交、依赖超时、节点崩溃、网络分区、消息重复或延迟、数据损坏、容量耗尽和区域故障。对每类问题说明检测、隔离、恢复、数据影响及用户体验。明确重试上限和退避、幂等范围、超时预算、降级条件、补偿方式、备份恢复目标。避免无界重试和把超时当作失败证明。

### 7. 解释取舍并验证

针对主要决策比较至少一个可行替代方案，说明收益、代价、适用条件和迁移成本。给出能验证假设的负载、故障、安全和恢复测试，以及上线后的指标与告警。说明先做什么、哪些数据会触发后续扩展，避免没有证据的过度设计。

## 二、常见设计主题速查

这些是可选工具箱，不是每题必选项。应先识别题目约束，再判断是否需要。

| 主题 | 适用信号 | 需要分析的边界与代价 |
| --- | --- | --- |
| 缓存 | 读多写少、可接受有限陈旧、后端读取已成瓶颈 | 缓存键、失效策略、击穿/穿透/雪崩、冷启动、数据陈旧容忍度、缓存故障时的保护 |
| 消息队列 | 生产与处理速率不同、可异步响应、需要解耦 | 投递语义、顺序范围、重复消费、积压、背压、死信、重放、消息与业务写入的一致性 |
| 数据分片 | 单节点容量或吞吐有证据地不足 | 分片键倾斜、跨分片查询/事务、扩容迁移、热点、故障域和运维复杂度 |
| 副本与读写分离 | 读扩展或可用性需求超过单副本能力 | 复制延迟、读己之写、故障切换、脑裂、确认级别和数据丢失窗口 |
| 幂等与去重 | 调用方重试、消息至少一次、外部副作用 | 幂等键作用域和有效期、并发竞争、状态约束、外部系统支持及过期后的重放 |
| 限流与隔离 | 突发流量或租户间资源竞争 | 维度、突发额度、拒绝语义、配额公平性、依赖池隔离和恢复策略 |
| 多区部署 | 区域故障目标或用户分布要求 | 同步/异步复制、写入归属、冲突处理、切换条件、RTO/RPO、演练成本 |
| 可观测性 | 需要维护 SLO 并快速定位故障 | 用户关键路径指标、日志上下文、分布式追踪、告警噪声、隐私和存储成本 |
| 搜索与分析 | 复杂检索或聚合不适合事务主库 | 索引延迟、重建、数据同步、查询成本、源数据权威性和新鲜度 |
| 分布式锁/事务 | 跨节点并发争用或多个资源需协调 | 锁过期与 fencing、死锁、部分成功、补偿、可用性及简化业务规则的可能性 |

## 三、设计完成前的自查

- 每条需求都能映射到组件责任、数据规则或验收方式。
- 每项容量数字有单位、输入假设和峰值口径。
- 核心用例和失败路径都能从图与文字中走通。
- 一致性、排序、重试、重复请求和状态转移有清楚定义。
- 有可观测指标、告警、容量保护、恢复和安全边界。
- 主要取舍解释了替代方案及其代价；复杂性与实际约束相称。
- 验收指标可通过测试或运行数据验证，且不会与题目给定条件矛盾。

## 四、练习节奏

每天只做一道题。先独立记录需求问题和假设，再完成一版设计；用评分标准自评，针对低分项修订并写下一个待验证风险。不要把背诵组件名称当作完成设计。复盘重点是需求如何改变决策、失败如何影响用户，以及哪些证据能验证设计。
